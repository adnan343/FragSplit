# Architecture and business rules

Next.js serves the storefront, product pages and metadata on the server. Client components handle cart storage, forms, accessible native dialogs and admin controls. The API is a modular ASP.NET Core application with EF Core and PostgreSQL. Admin and customer roles use ASP.NET Core cookie authentication and Identity password hashing. Customers can check out as guests or register with an email and password. A signed-in customer can save a delivery profile, resume a bag and track orders on another device. The account ID in the authenticated session establishes ownership. A customer can claim an earlier guest order by opening its private receipt and choosing to save it. Account recovery uses a random single-use code shown at registration and rotated after a reset. Only its hash is stored. Resetting the password or signing out on all devices invalidates earlier customer sessions.

## Catalog and images
The three fixed categories are domain values. Brand names and category names live on the perfume row. Each listing has five independently priced variants and an enabled flag per size. Stock is integer ml on the perfume row. Listing queries use the cheapest enabled size that fits available liquid, stable pagination and server-side sorting. The first gallery image is primary. Signed-in admins upload files with an alt description. The API checks byte length, decoded format and pixel count and rewrites supported inputs as metadata-free WebP. A storage interface handles a local volume or an S3-compatible bucket. Detaching a gallery entry makes its media route unavailable. Periodically compare unreferenced objects to database references before lifecycle deletion.

## Checkout and inventory
The guest cart stores product IDs, sizes and display prices on the device. Authenticated bags store product IDs, sizes and quantities in PostgreSQL. Signing in merges the device bag, keeping the larger quantity for overlapping sizes. A cart version prevents stale devices from overwriting later edits. Account checkout checks that version and clears the purchased bag in the order transaction. Checkout rereads current prices, region, delivery charges, enabled sizes and aggregate ml. An order requires a matching quote fingerprint and acknowledgment. A random client submission key and payload fingerprint make retries safe. PostgreSQL transaction advisory locks serialize the same request key. Ordered row locks serialize competing operations on each perfume. One database transaction writes order snapshots, reserves total ml per perfume and appends the ledger. Money uses PostgreSQL numeric(12,2).

Available liquid equals on-hand minus reserved. A reserve increases reserved. Release reduces reserved. Consumption reduces both reserved and on-hand. Approved recovery increases on-hand. A database check enforces nonnegative balances. Each movement has a unique operation key and an actor or order reference. The order stores its reservation state and deadline, and immutable order lines provide the quantity per perfume. Order row locks and state guards make callbacks and retries idempotent.

COD reserves on submission and consumes on admin confirmation. Its payment stays unpaid until delivery and a separate collection action. Online payment consumes only after provider validation and a live reservation. The expiry worker checks every 30 seconds in bounded batches. An expired deadline prevents consumption even before the worker runs. Late or risky charges go to manual review and any held stock is released. Unknown initiation outcomes keep their original attempt for reconciliation.

## Fulfillment and refunds
Normal progression is Pending → Confirmed → Processing → Shipped → Delivered. Online verification may perform confirmation. Cancellation is allowed before delivery. Delivery may transition to Returned. Cancel or return requires a reason. A reservation is released. Already consumed stock returns only with explicit physical recovery approval. Admins record a full refund after the external refund has actually been performed. Partial refunds and automated provider refund requests are outside the current workflow.

## Reporting
All calendar filters include both endpoints in Asia/Dhaka. UTC timestamps are persisted. The dashboard uses cash-basis receipt and refund dates for financial results and order creation date for placement counts. Gross receipts include collected COD and verified online charges, including shipping. Recorded refunds subtract the full order amount on refund date. Net sales equal gross receipts less refunds. Risky or unfulfillable charges held for reconciliation are excluded from sales and their later refunds are excluded as well. Unpaid COD awaiting collection is an outstanding amount on noncancelled, nonreturned orders placed in the range. Product, size and category groups use purchase-time merchandise prices and quantities and reverse merchandise on the refund date. Low-stock counts reflect current active inventory. Dashboard totals and public best sellers can differ because the latter rank currently paid, noncancelled, nonreturned purchases across all dates.
